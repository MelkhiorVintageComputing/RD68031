# The coprocessor interface

MC68030 UM section 10, as built. Re-derived from the MC68030 manual at M12: the
protocol is the MC68020's, word for word where it matters (the two sections were
compared line by line, and every difference is in the list below), and what the
MC68030 adds is around it -- synchronous CIR cycles, the caches and the MMU. "UM"
here is `MC68030UM_split`; figure and table numbers are section 10's.

`COPROCESSOR = 1` on `rd68031_top` builds the interface; with `COPROCESSOR = 0`
every F-line word with a CpID other than zero is an F-line exception, which is also
what a machine with no coprocessor wants (UM 10.5.2.8). The microcode is the same
either way: the parameter only chooses what the opcode decoder hands the sequencer
for an F-line word.

**CpID 0 is never the coprocessor interface's** (since M5). UM 10.1: "F-line
operation words, in which the CpID is zero, are not coprocessor instructions for the
MC68030 ... The MC68030 never generates coprocessor interface bus cycles with the
CpID equal to zero"; UM 7.4.3: "these cycles can only be generated by the MOVES
instruction". CpID 0 is the on-chip MMU's, and goes to the opcode decoder whatever
`COPROCESSOR` is: the four MMU instructions' first words (type 000, an effective
address field of zero or control alterable) to `mmu_op`, every other CpID-0 word to
`cp0_unimp` (`tools/ucode/program.py`). Both take a privilege violation in user mode
before reading any extension word (UM 9.8, 8.1.5, 8.1.6), and `cp0_unimp` an F-line
exception in supervisor mode. `core_m030_tb` checks that no CPU-space cycle ever
names CpID 0, with the interface built and without. CpIDs 1 to 7 are the
interface's.

`make cpif` runs `core_cpif_tb` against a scripted coprocessor, 620 checks: the
MC68020's protocol (`sim/tb/core_cpif_tb.sv`) and, since M12, what the MC68030 adds
(`sim/tb/core_cpif_m030.svh`; `+m030_only` runs that part alone). `make sim
COPROCESSOR=1` builds the interface into every other core testbench.

## What the MC68030 changed

Section 10 of the MC68030 manual against section 7 of the MC68020's, line by line.
Everything else is the same text.

| UM | The MC68030 says | Here |
|---|---|---|
| 10.1, 10.2, 7.4.3 | CpID 0 is the MMU's, never a CIR cycle | since M5, above |
| 10.1.1, 10.1.4.2 | a coprocessor "can use either the asynchronous or synchronous bus interface"; "the MC68030 accesses the registers in the CIR set using standard asynchronous or synchronous bus cycles" | a CIR cycle is an ordinary operand cycle, ended by DSACK or by STERM -- tested both ways |
| 10.1.4.3 | "the MC68030 never requests a burst operation during a coprocessor (CPU space) bus cycle" | `rd68031_biu` never asserts CBREQ with FC = 7 (`next_brq`), and the data cache never asks for a fill there (`lk_space_ok`) -- tested with DBE on, on a synchronous coprocessor |
| 10.1.4.3 | "nor does it internally cache data read or written during coprocessor (CPU space) bus cycles" | `rd68031_dcache` neither looks up nor fills nor updates a line for FC = 7 -- tested by reading the operand CIR twice with the data cache on |
| 10.1.4.3 | "the MC68030 drives the three function code outputs high (FC2:FC0 = 111)" | as before |
| 10.4.15 | "the selected registers are transferred in the order D0-D7 and then A0-A7" | the order built at M13; the MC68020 manual's "D7-D0 and then A7-A0" was the contradiction RD68021 recorded, and the MC68030's says what was chosen |

And from the other sections:

- **The MMU** (UM 9.2.1, figure 9-8): "a CPU space address (FC0-FC2 = $7) is a
  special case that is immediately used as a physical address without
  translation" -- the flowchart's first branch, ahead of the caches, the TTx
  registers and the ATC: "PA <- LA, CIOUT <- 0". So a CIR cycle is never
  translated, never searched for, never matched by TT0 or TT1, and never has CIOUT
  asserted (`rd68031_mmu_xl`). The operands a primitive moves to and from memory
  are ordinary data accesses: translated, checked, cached, and faulted like any
  other (below).
- **The data cache** (UM 6.1.2): "the data cache stores data references to any
  address space except CPU space". The operands are cached as any data is, and a
  write the coprocessor asks for goes through the cache as any write does.
- **The frames** (UM 8.4, Table 8-6) are the MC68020's: the four-word frame
  (format $0) for pre-instruction exceptions, F-line and privilege violations and
  format errors; the six-word frame (format $2) for post-instruction exceptions and
  cpTRAPcc; the ten-word coprocessor mid-instruction frame (format $9) for the
  mid-instruction primitive, a protocol violation and an interrupt in the dialogue;
  the long bus fault frame (format $B) for a bus error on a CIR access past the
  first or on an operand. RTE out of format $9 "reads from the response register of
  the coprocessor that initiated the exception" (UM 8.1.13).

## How it is built

A coprocessor instruction is a conversation. The processor starts it with one
access to an interface register (a CIR), reads the response CIR, does what the
primitive there says, and reads it again until a primitive lets it go.

**CIR accesses** are ordinary operand requests in CPU space type $2, with the CpID
from bits 11:9 of the operation word on A15-A13, the register on A4-A0, and every
other address line zero (UM figure 10-3). Being ordinary, they take whatever the
bus offers: dynamic bus sizing (the MC68881 answers its word registers on a
sixteen-bit port, MC68881 UM 7.2), wait states, DSACK or STERM. Being in CPU space,
the bus unit synthesises their address (`cpu_space_addr`), asks for no burst, and
the MMU and the data cache leave them alone. The microword's `cpuspace` field is
one of two values:

| | a bus error on it | used for |
|---|---|---|
| `CPINIT` | an answer: the microcode tests the end code and takes an **F-line** exception -- "the main processor assumes that the coprocessor is not present" (UM 10.5.2.8) | the one access that starts each instruction |
| `COPROC` | a **bus error**, with the long frame, and RTE reruns the access | every other one |

The bus unit carries the difference as `req_cpfault`. No other CPU-space bus error
is a fault, because on an interrupt or breakpoint acknowledge it is an answer.

**The primitive decoder.** A primitive read from the response CIR decides which
register is read next, which way an operand moves, and whether the effective
address is evaluated. All of those are decisions that steer the bus. So the
primitive is held in `cprim` and decoded in hardware into a micro-address,
`rd68031_cpdec_rom`, reached with `seq = CPDEC`. This is the extension-word
decoder's trick on a different word. Its inputs are twenty-two bits:

- **the category**, because most primitives with CA clear, and some primitives at
  all, are protocol violations in a conditional instruction (UM table 10-6);
- **the primitive itself**, all sixteen bits, so that the decoder also serves:
  - the PC bit, first, through `cp_passpc`, which passes the program counter and
    clears the bit before dispatching again;
  - every case of the null primitive: come again, come again with interrupts
    allowed, a conditional's verdict, finished, not finished;
  - the length: four bytes (a control register) and twelve (the extended format)
    have handlers of their own, with no count and no loop;
- **five bits about the instruction's effective address**: in the class the
  primitive names (table 10-4), suitable for transferring multiple coprocessor
  registers (UM 10.4.16), and which of Dn, An, #imm, (An)+, -(An) or the other
  memory modes it is. A primitive that takes an effective address goes straight to
  the handler for its kind.

Everything the manual leaves undefined is decoded as a protocol violation. The
decoder's inputs are all registers -- `cprim` and stage D -- and it costs no clock:
`doc/size-and-speed.md`.

**The end of a primitive** is one question, `CPAGAIN` -- CA set, or a trace on
instruction execution pending (UM 10.5.2.5, below) -- on the primitive's own last
microword: back to the response CIR, or a release that is the next microword.

**The dialogue's state** is four things, and they are the four that the
mid-instruction frame (UM figure 10-43) saves. That is what lets an interrupt be
taken in the middle of it and the dialogue resumed after RTE:

| | where it is | frame |
|---|---|---|
| the program counter | `pc_d`: stage D holds the F-line operation word for the whole instruction and nothing advances it | +$08 |
| the scanPC | the address of stage C (UM 10.4.1). Every word the instruction reads from the stream is consumed, which moves it on | +$02 |
| the operation word | stage D | +$0E |
| the evaluated effective address | `EA`, for the write-to-previously-evaluated-address primitive | +$10 |

`+$0C`, the "internal register", carries what the instruction had decided about
tracing: the trace mode it began with, whether it has changed the flow, and whether
it is exempt (bits 1:0, 2, 3 and 4). A resumed dialogue has to trace the same way.

Within one primitive T0-T3 are scratch, and the primitive itself is in `cprim`,
which the long fault frame carries at +$4A (`doc/checkpoint.md`). A bus error on an
operand a primitive is moving is an ordinary bus error (UM 10.5.2.8), and RTE goes
back into the middle of the primitive.

**The scanPC written by the coprocessor** (UM 10.4.17) refills the queue behind
stage D from the new address and leaves stage D and `pc_d` alone. It goes over the
checkpoint port as `CK_SCAN`, and it is also the last thing RTE puts back out of a
format $9 frame. Written with an odd address, the refill is an address error at the
next use of the pipe, as UM 10.5.2.8 says.

**Operands** move in long words, with the remainder in one transfer of one to three
bytes. The count is a microword constant, so the tail is a branch on the low two
bits of the count. Every part goes to or from offset $10, which puts it on the top
lanes of the operand CIR (UM figure 10-21). The bus unit splits any part that is
misaligned on the memory side, as it does for any operand.

The interface register writes past the first are posted, as data writes are
(`doc/checkpoint.md` rule 9): their bus error is an ordinary one, and RTE reruns it
in CPU space. So is a memory write that carries what an operand CIR read just
returned.

Four and twelve bytes, the shapes an MC68881 asks for most, go through unrolled
handlers: one memory access and one CIR access per long word.
- **To the coprocessor:** the read steps the address.
- **From it:** the write's ALU carries the data, so the CIR read steps the address,
  into T3 and T2 by turns.

Other lengths use the general loop.

### The operands and the MMU

The memory side of a primitive -- evaluate effective address and transfer data,
write to previously evaluated effective address, take address and transfer data,
transfer to/from top of stack, transfer multiple coprocessor registers, cpSAVE's
and cpRESTORE's state -- is a data access in the space the primitive names (UM
10.4.10, 10.4.11: "supervisor or user data space according to the value of the S
bit"; the effective-address forms in the instruction's own space, program space for
a PC-relative read). It is translated, and the coprocessor sees only logical
addresses: the evaluate and transfer effective address primitive hands it the
logical address, and the address it supplies through the operand address CIR is
logical too.

A page the MMU refuses is a bus error before AS, as for any operand (UM 9.2.1,
9.5.2): the long frame (format $B), DF set, the fault address at +$10, the
primitive being served at +$4A. A handler that maps the page and returns with DF
still set reruns the faulted access, and the primitive goes on from it (UM
10.5.2.8: "the main processor can return to the point in the coprocessor
instruction at which the fault occurred"). Nothing before it is repeated: the
operand CIR accesses already made are not made again, and -(An) is not stepped
again (`doc/checkpoint.md` rules 2 and 9). A posted write faulted in the second
page of an operand is rerun from its own cycle, as for any write.

## The instructions

| | opcode | effective addresses | starts with |
|---|---|---|---|
| cpGEN | `1111 ccc 000 eeeeee`, command | any: only a primitive looks at it | the command word to the command CIR |
| cpBcc.W / .L | `1111 ccc 01s cccccc` | -- | the operation word to the condition CIR |
| cpScc | `1111 ccc 001 eeeeee`, condition | data alterable | the condition word to the condition CIR |
| cpDBcc | `1111 ccc 001001 rrr`, condition, displacement | -- | likewise |
| cpTRAPcc | `1111 ccc 001111 ooo`, condition, 0-2 words | -- | likewise |
| cpSAVE | `1111 ccc 100 eeeeee` | control alterable, -(An) | a read of the save CIR |
| cpRESTORE | `1111 ccc 101 eeeeee` | control, (An)+, #&lt;frame&gt; | the format word to the restore CIR |

A type of 110 or 111 and an effective address the form does not allow are F-line
exceptions with no CIR access (UM 10.5.2.2). cpSAVE and cpRESTORE are privileged,
and that is checked before any CIR is touched (UM 10.2.3.3.2, 10.2.3.4.2,
10.5.2.3) -- in a core built without the interface too.

A conditional instruction's dialogue ends with a null primitive with CA clear. The
verdict is TF, and which instruction's tail runs is read off stage D.

**cpSAVE** writes the format word as a long word with its reserved half zero, then
the state from the top down: the first long word read from the operand CIR goes to
the highest address (UM 10.2.3.1: "to descending memory addresses"). Not ready on
cpSAVE is busy's path (below). The invalid format word, a reserved code ($03-$0F,
"interpreted as invalid format words"), and a valid one whose length is not a
multiple of four are each the abort mask and a format error (UM 10.2.3.2.3,
10.5.1.5, 10.5.2.7).

**cpRESTORE** reads the format word from memory, writes it to the restore CIR,
reads the coprocessor's answer, and then moves the state in ascending order. The
length it uses is the one from memory (figure 10-18, note 2), and a length that is
not a multiple of four is refused only after the answer has been read (UM
10.5.2.7). Not ready from the restore CIR reads it again at once, "without
servicing any pending interrupts" (UM 10.2.3.2.2). The invalid format word, and a
reserved code, are the abort mask and a format error.

## The primitives

UM 10.4, and the test in `core_cpif_tb` that drives each one.

| Primitive | bits 13:8 | served by | tested |
|---|---|---|---|
| busy | `100100` | the instruction starts again: with an interrupt pending, from its operation word's address, so that the interrupt is taken first with the four-word frame; with none, from stage D as it stands (the breakpoint case below) | yes: general and conditional, with and without an interrupt, and after a breakpoint acknowledge |
| null | `00100i` | CA=1: read again, servicing an interrupt first if IA; CA=0: release a general instruction (or keep reading while a trace on instruction execution is pending), or finish a conditional one on TF | yes: release, come-again, IA with an interrupt on each stack, trace pending, trace on change of flow |
| supervisor check | `000100` | at the user level: abort, then a privilege violation | yes |
| transfer operation word | `-00111` | stage D to $08 | yes |
| transfer from instruction stream | `-01111` | the stream to the operand CIR in long words and a word; odd lengths are refused | yes |
| evaluate and transfer effective address | `001010` | control alterable only, or abort and F-line; the (logical) address to $1C | yes, both, with the MMU on and off |
| evaluate effective address and transfer data | `d10vvv` | the class check of table 10-4, then a data or address register (one, two or four bytes), an immediate (one byte or even), (An)+ and -(An) stepped by the length, or any other memory mode | yes: every one of those; through a mapped page, and faulted on a refused one |
| write to previously evaluated effective address | `100000` | the operand CIR to `EA`, in data space | yes, with the MMU on and off |
| take address and transfer data | `d00101` | the address from $1C, then the operand | yes, with the MMU on and off |
| transfer to/from top of stack | `d01110` | (A7)+ or -(A7), a byte stepping by two | yes |
| transfer single main processor register | `d01100` | a long word | yes, both ways |
| transfer main processor control register | `d01101` | the select code from $14 through the same multiplexer as MOVEC; a code not in table 10-5 is a protocol violation | yes |
| transfer multiple main processor registers | `d00110` | the mask from $14, walked D0-D7 then A0-A7 (UM 10.4.15) | yes, both ways |
| transfer multiple coprocessor registers | `d00001` | one operand per set bit; -(An) walks the operands down and each operand's bytes up (figure 10-38); a mode the direction does not allow is abort and F-line | yes, to -(An), from (An)+ and a control address, and -(An) refused |
| transfer status register and scanPC | `d0001s` | out: the scanPC, then the SR; in: the SR, then the scanPC, which refills the queue in the space the new SR says | yes, both ways, and an odd scanPC |
| take pre-instruction exception | `-11100` | acknowledge, then the four-word frame with the operation word's address | yes |
| take mid-instruction exception | `-11101` | acknowledge, then format $9; RTE reads the response CIR again | yes |
| take post-instruction exception | `-11110` | acknowledge, then format $2 with the scanPC as the program counter | yes |

The PC bit is served before anything else, including an exception the primitive
leads to (UM 10.4.2) -- tested with an undefined primitive. A protocol violation
the processor detects is not written to the control CIR (UM 10.5.2.1). The aborts
write $0001 and the acknowledge $0002 (UM 10.3.2: the masks 01 and 10); the
fourteen undefined bits are zero.

**Busy after a breakpoint** (UM 10.4.3): "when a breakpoint acknowledge cycle
initiates a coprocessor F-line instruction, the coprocessor returns the busy
primitive in response to the instruction initiation, and an interrupt is pending
... the processor re-executes the breakpoint acknowledge cycle after the interrupt
exception processing has been completed". So `cp_busy` asks whether an interrupt
is pending. If one is, the pipe is refilled from the operation word's address, the
interrupt is taken there with that address in the frame, and RTE comes back to the
breakpoint, whose acknowledge runs again. If none is, stage D -- which holds the
word the acknowledge supplied, when there was one -- is decoded again where it
stands, and only the queue behind it is refilled, from the word after it (the
scanPC refill of UM 10.4.17, which leaves stage D alone). For an instruction that
did not come from a breakpoint the two are the same thing. Not ready on cpSAVE takes
the same path (UM 10.5.2.6). Until M12 busy always refilled from the operation
word, and a breakpoint's acknowledge ran again on every busy (`doc/bugs-found.md`).

**Tracing** (UM 10.5.2.5). With a trace on instruction execution pending (T1 set,
the mode the instruction began with) a general instruction's dialogue is held open
past CA = 0 until a null primitive with PF set, servicing interrupts on IA, so that
the trace is taken only when the coprocessor has finished. A trace on change of
flow does not hold it: under T1 T0 = 01 "a trace exception is taken for the
instruction only when the coprocessor issues a transfer status register and
scanPC primitive with DR = 1 ... it is possible that the coprocessor is still
executing the cpGEN instruction concurrently when the main processor begins
execution of the trace exception handler". So the dialogue ends at the first CA = 0
as it would untraced, and the trace is taken at the boundary (`trace_hold` in
`rd68031_seq`, against `trace_take`). Until M12 the change of flow held the
dialogue too (`doc/bugs-found.md`). Conditional, cpSAVE and cpRESTORE dialogues are
not changed by a pending trace at all.

|---|---|---|---|

| F-line from a primitive | abort, $0, the instruction | 11 | the instruction again |

| cpTRAPcc true | $2, the next instruction | 7 | on |

## What was chosen where the manual does not say

`doc/manual-contradictions.md` has the ones where the manual says two things.

- **cpRESTORE of an immediate** is allowed: UM 10.2.3.4.1 allows "all memory
  addressing modes except the predecrement", which includes it, and PRM 6's table
  does; PRM 6's prose does not.
- **The transfer multiple coprocessor registers modes** are UM 10.4.16's: to the
  coprocessor, control and (An)+; from it, control alterable and -(An). Table
  10-6 swaps the two increment modes, against the text and figure 10-38.
- **The reserved word after the format word** is written as zero. UM figure 10-14
  calls it "unused, reserved", and the MC68881 manual says only that it is there
  for alignment.
- **Primitive encodings $27, $2F and $3C-$3E in bits 13:8** are neither drawn nor
  listed as undefined in UM 10.6. They are taken as the primitive with the DR bit
  ignored: transfer operation word, transfer from instruction stream, and the three
  take-exception primitives.
- **The frame format of a CIR bus error** is the long one: the fault is always
  mid-instruction.
- **cpRESTORE's "empty"** is the coprocessor's answer: a valid format word in
  memory answered with the empty/reset format word moves no state, and (An)+ steps
  past the format word alone.

## What is not checked

- **There is no oracle.** None of the oracle flows is used for this protocol. The
  only check is the scripted coprocessor (`sim/models/rd68031_cpmodel.sv`),
  written from UM section 10 and cross-checked against the other side of the
  protocol in `MC68881UM_split/11-section-07-coprocessor-interface.pdf`. A
  misreading shared between the model and the core is invisible. The model is
  deliberately thin, a queue per register and a log, so that each test states the
  protocol it expects rather than inheriting it from the model.
- **A real MC68881 or MC68882.** RD68021 checked a whole machine with an MC68881
  front end in TME (`make sunos-fpu`); that harness was not carried over, and the
  floating-point coprocessor comes back with the lockstep platforms (M13, M14).
- **Concurrency.** This processor never overlaps its own execution with a
  coprocessor's, because the dialogue holds the sequencer. What the manual allows a
  coprocessor to do concurrently, it can still do: the processor is released after
  CA = 0.

## Area and clock

Measured on RD68021 at its M13, Artix-7, under the 60 ns constraint of the time:
the interface cost 493 Slice LUTs (7 %) and took the clock from 22.72 to 22.28 MHz.
`doc/implementation.md` has today's figures, all with the interface built.
`COPROCESSOR = 0` does not give either back -- it only makes F-line words F-line
exceptions.

## Cycle counts

UM section 11 gives no counts for coprocessor instructions, which depend on the
coprocessor. It gives one for RTE out of a coprocessor frame: 26 clocks on the
MC68030 (UM 11.6.18, seven reads), where `make cycles` still shows the MC68020's 31
until M15 retargets its rows (`doc/timing-divergences.md`).

`make cycles` measures twelve instructions against the scripted coprocessor. It
answers as an MC68881 does, at once and with no time of its own, so the rows are
the processor's own clocks. MC68881UM tables 8-6, 8-7 and 8-8 are listed beside
them for scale; they include the FPU's own time, so they are a ceiling, not a
like-for-like. M12 changed none of them: busy and a pending trace are the only
paths it touched, and no row has either.

| | RD68021 before its M13 tuning | now | MC68881UM, cache case |
|---|--:|--:|--:|
| FNOP | 22 | 18 | 18 |
| FBEQ.W taken / not taken | 25 / 22 | 21 / 18 | 20 / 18 |
| FSEQ D0 | 26 | 22 | 18 |
| FMOVE.L D0,FPCR | 34 | 25 | 28 |
| FMOVE.L FPCR,D0 | 35 | 27 | 31 |
| FMOVE.L (A0),FPCR | 51 | 29 | 33 + 2 |
| FMOVEM.L FPcr*3,(A0) | 75 | 45 | 27 + 18 + 2 |
| FMOVEM.X (A0),FP0-FP2 | 165 | 96 | 35 + 93 + 2 |
| FMOVEM.X FP0-FP2,-(A7) | 161 | 97 | 37 + 75 + 6 |
| FSAVE -(A7), idle | 88 | 63 | 52 + 6 |
| FRESTORE (A7)+, idle | 96 | 72 | 57 + 6 |
